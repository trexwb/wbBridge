## 二、已知限制

| # | 限制 | 说明 |
|---|---|---|
| 1 | **免费模型名单、额度与可用性由上游决定** | 本应用不控制也不缓存上游额度；模型可能随时增减或不可用 |
| 2 | **未做商用代码签名 / 公证** | Windows 可能提示未知发布者；macOS 需按放行说明操作（ad-hoc 签名） |
| 3 | **Windows ARM64 / Linux 包未实机验证** | 已由 CI 构建并随 Release 发布，但没有在真实 Windows / Linux 机器上装过、冷启动过 |
| 4 | **仅 PAC / SOCKS 代理暂不支持** | 系统代理仅支持 macOS `scutil` / Windows 注册表解析出的手动 HTTP/HTTPS 代理 |
| 5 | **浅色主题 3 处对比度未达标** | 副标题、页脚说明、耗时行仍用 `--muted`，对比度低于 WCAG AA 的 4.5:1 |
| 6 | **`cargo fmt --check` 全仓不干净** | **未作为门禁**；代码风格以 clippy 0 warning 为准 |
| 7 | **探测会消耗少量免费额度** | 免费模型检测会向每个模型发送简短真实请求 |
| 8 | **单实例锁约束** | `service.pid` 指示进程存活时重复启动会失败（独立进程退出码 2），不会抢占端口；锁的判定是红线、不得绕过。Windows 上的异常现象见未验证项第 13 条 |
| 9 | **版本号值域** | 产品版本 = 核心 crate 版本 = **1.2.0**（7 处落点，由 `version:set` / `version:check` 统一；段位取值的由来见第 21 项）；`status.json` 中的 `version` 是历史沿革值 **0.2.0**（界面上可见），**不得**顺手改 |
| 10 | **仓库提交状态** | 分支 `dev`（远端 `origin = https://github.com/trexwb/wbBridge.git`，另有 `main`）；提交由用户决定，Agent 不自动 `git commit` / `git push` / `git tag` |
| 11 | **Node 仅用于前端构建** | Node.js >= 24 **只**服务 Vite 构建与 `scripts/*.mjs`；核心运行不依赖 Node，也不得把 Node 运行期重新引入核心链路 |
| 12 | **v1.0.1 及更早的用户收不到自动更新** | 那一版没接 updater（产物无 `.sig`、面板无更新区），必须由用户手动下载安装包升级一次 |
| 13 | **更新通道受 Draft 闸门控制** | endpoint 指向 `releases/latest/download/latest.json`，而 GitHub 的 `releases/latest` **不含 draft 与 prerelease**——人工点 Publish 之前老客户端拿到 404 属预期（draft 即灰度闸门），不是"更新功能坏了" |
| 14 | **面板偏好只持久化三项** | 当前视图、「启动后自动检查更新」开关，以及 **AI 助手的非凭据配置**（`ai` = `brain` / `baseUrl` / `model` / `selfModel` / `tools`）（`src/core/prefs.js`，键前缀 `wb.` + 字段白名单 + 2KB 上限）。**助手端点的 API Key 没有白名单键，结构上落不进 `localStorage`**，只存在于 `AssistantView` 的会话内存，重启需重填。详情栏收起状态与窗口尺寸 / 位置**不持久化**（后者需 `tauri-plugin-window-state`，与 `quit_app` 关停时序的交互无法在无 GUI 验证下确认）。**别混淆**：系统代理开关与 WorkBuddy 配置文件路径由**核心**持久化在数据目录 `settings.json`，与面板 `localStorage` 无关 |
| 15 | **存储里绝不写凭据** | `prefs.js` 的写入路径只接受白名单键、且对值做字段投影（如 `update` 只留 `autoCheck` / `lastCheckedAt`）；`api-key`、`OPENCODE_SERVER_PASSWORD`、models 文件路径等一律进不了 `localStorage`（有对应单测钉住） |
| 16 | **面板状态发布为帧级合并** | 壳发来的 `core-status` / `core-activity` / `core-failed` 入队后由 `requestAnimationFrame` 每帧最多 flush 一次（无 rAF 环境回落 16ms `setTimeout`）：合并语义与逐个执行等价、最终取值不变，但面板可见状态最多滞后约一帧——排查「面板看起来慢半拍」先想到这条 |
| 17 | **验签只认 `pubkey` 的第一条公钥** | 多嵌几条**不构成**轮换白名单（`minisign-verify` 的 `PublicKey::decode` 只读解码文本前两行）；**换签名钥必须同一次发布里同步替换 `pubkey`**，且已发布的老客户端只认它自己内嵌的那条。当前只嵌 `2B11F78BEA8A43F` 一条 |
| 18 | **macOS 的 `.dmg` 不经 Tauri** | `bundle.targets` 为显式列表（不含 `dmg`），dmg 由 `npm run make:dmg`（`scripts/make-dmg.sh`，hdiutil）生成；交叉构建**必须传 `TARGET_TRIPLE`**；macOS 27 上 hdiutil 会打 `deprecated … use diskutil image` 告警，产物正常，暂未改造 |
| 19 | **插件配置没有任何自动回滚点** | `sync.rs` 的写路径**不产生任何 `.bak`**，保护只剩「文件锁 + 写前二次读取 + 原子替换（同目录临时文件再 `rename`）」。`sweep_old_backups(file)` 在**两条出口**都调用（成功写盘后、内容无变化的早退前），按**逐段白名单**（文件名以 `<配置文件名>.buddy-bridge-` 开头、以 `.bak` 结尾、中段全是 ASCII 数字、必须是普通文件；跳过目录、`read_dir` 失败静默）只清理本工具**旧版**攒下的存量备份，用户自己的 `*.bak` 绝不碰。⚠ 风险如实告知：配置被本工具写坏时**没有自动回滚点**，唯一兜底是原子替换本身；WorkBuddy 与 CodeBuddy 共用这条写路径，两边一起生效 |
| 20 | **发布说明不进更新清单** | 工作流的 Release 正文是硬编码一句「WB Bridge — 让 WorkBuddy 使用 OpenCode 免费模型。」再叠加 `generate_release_notes: true`（GitHub 按 commit 历史自动生成）；`latest.json` **没有 `notes` 字段**（只有 `version` / `pub_date` / `platforms`）——任何「发布说明会随更新清单推送给用户」的说法都不成立 |
| 21 | **`1.2.x ~ 1.3.x` 段位：2026-10-13 改判后重新启用** | 该段位曾被裁定「作废、不得再占用」（当时产品写法已推进到 1.4.x）。**维护者于 2026-10-13 明确指令把版本号回退到 1.2.0**，旧裁定随之作废（`AGENTS.md` 的同名条目已同步改写）。改判的可核对依据：`git tag` 最高只到 `v1.1.15`，`v1.2.0` 从未存在、该段位从未构建也从未打标签，因此不与任何已发布产物或已推送标签冲突。此前写过的 `1.4.0`（AI 助手）、`1.4.1`（同轮面板修复）、`1.5.0`（助手 UI/UX 深化）**一并弃用**——这三段产物同样从未构建、从未打标签，其内容全部落在当前的 1.2.0 里；后续推进自 1.2.0 起按 `AGENTS.md` 的强制递增规则走，**不得**再跳回 1.3.x/1.4.x/1.5.x |
| 22 | **`WB · auto` 的 `maxInputTokens` 取池内最小值** | 混搭池里可能把长上下文请求提前截断（容量浪费问题，尚未针对性修复）；`supportsToolCall` 取自池内能力（`auto::any_tool_capable`，与 `auto.rs` 私有的档位谓词同源），**随池变化**而非固定 `true` |
| 23 | **`WB · auto` 的三条已知缺口** | ① 路由选择的运行日志行未做（`log_line` 属编排层私有、`Handlers` 无日志通道）；② router 级请求体超时不摘除模型的单测未做（`REQUEST_BODY_TIMEOUT` 在 `chat()` 里硬编码 20s）；③ 上游挂死且客户端不取消时，该模型既不失败也不被摘除 |

## 三、不该被描述为"已实现"的事

为避免文档与界面口径失真，以下内容**严禁**在其他页面或对外说明中被当作已完成功能：

- ❌ 宣称「自动更新已端到端可用」（「检查 → 下载 → 安装 → 重启带新版本起来」尚未真实走过），或把「产出了 `.sig`、CI 全绿」当成客户端验签通过；
- ❌ 宣称面板逐视图的版式 / 对比度 / 交互已系统性核验达标（应用已实机运行，但逐视图走查未做）；
- ❌ 宣称接入了商业代码签名或 Apple 公证（文档只有**接入位置与所需变量清单**，配置里没有这些键）；
- ❌ 宣称 Windows 的「反复退出码 2」已定位或已修复（**未取证、未修**，只有临时恢复步骤）；
- ❌ 宣称「同步失败还能自动回滚到上一份配置」（当前完全不写备份），或宣称补建出来的空 `models.json` 已被插件自身成功读入；
- ❌ 宣称「发布说明会随更新清单推送给用户」（`latest.json` 没有 `notes` 字段，Release 正文是硬编码一句 + `generate_release_notes` 自动补）；
- ❌ 把 `status.json` 中的 `0.2.0` 当作产品版本；
- ❌ 宣称已支持 PAC / SOCKS 代理；
- ❌ 宣称 `localStorage` 偏好已在真实 WebView 里验证过，或宣称「更新失败后的一次真实回滚」已走过；
- ⚠️ 宣称「平台聚合发现 / `Provider.models` 权威清单 / 上游失败中文文案在真实 GUI 链路下**完整**跑通过」不成立：GUI 内「输入 Key → 保存 → 热生效 → 探测通过 → 插件真实对话」这条逐环节链尚未点过；文案判定与清单过滤的证据层级是单测 + 本机沙箱；
- ❌ 宣称九项待决策项（A~I）中的任何一项已解决；
- ❌ 宣称「AI 助手能代管 WB Bridge」已实机跑通：面板从未在真实 WebView 里发出过一次助手请求，本机大脑（默认 `WB · auto`）与外部端点都**零实测**，18 条工具（含停止核心、下载安装更新、重启生效三条高危）的执行效果只有单测与构建证据（见未验证项第 17 项）。可以说的是「入口已实现、协议与校验已单测钉住」，不能说「已验证可用」；也不得把助手的 18 条工具描述成「面板之外的新能力」——它们全部复用既有的 `core_action` 链路。

## 四、如何把这些边界用起来

- **提交 / 发布前**：对照[版本与发布](版本与发布)的「发布前检查清单」逐项执行。其中「实机启动 GUI」已完成；「产出安装包」本机只做过 macOS aarch64，其余平台的包由 CI 产出，**Windows / Linux 仍待实机安装与冷启动**；推标签之前必须先确认 GitHub 仓库级 Variables 已配好签名私钥全文与非空口令（缺任一项会在整套 Rust 编译跑完后的打包那一步才失败），并遵守「先版本推进提交、再在该提交上打标签」的顺序。
- **排查问题时**：先确认自己处在哪种运行形态（见[常见问题与故障排查](常见问题与故障排查)）。
- **完成任一未验证项后**：同步更新本页与 `README.md`——本页是这些边界的唯一登记处。
