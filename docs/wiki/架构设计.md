# 架构设计

本页说明 WB Bridge 的分层结构、壳与核心的边界、IPC 契约与数据落点。所有内容以仓库真实代码为准（`AGENTS.md`、`docs/contract.md`、`src-tauri/src/lib.rs`、`src-tauri/core/src/*`）。

## 分层结构（唯一权威源：`AGENTS.md`）

三层结构表（核心 / 控制面板 / 桌面壳）、核心不做 sidecar（`bundle.externalBin` 为空数组、`src-tauri/binaries/` 已删除）以及「核心为什么保持独立 crate」的说明，唯一正文在 `AGENTS.md` 的「项目概述与定位」与「目录结构说明」；本页不再复制。本页只保留壳与核心之间的契约与数据落点。

## 进程模型与各链路时序（唯一权威源：`AGENTS.md`）

核心的**进程模型**、**启动时序**（`src-tauri/core/src/orchestration.rs`）、**请求链路**（`/v1/chat/completions`）、**模型发布链路**与 **OpenCode 运行时隔离链路**的唯一正文在 `AGENTS.md` 的「核心架构与数据流」一节（含「关键常量（改动前必须确认语义）」表）；本页不再复制，读代码或排查前请先读该节。

## 壳与核心的边界

### IPC 命令与事件（面板 ↔ 壳）

| 命令 / 事件 | 方向 | 说明 |
|---|---|---|
| `core_refresh` / `core_probe` / `core_import` / `core_system_proxy` / `core_shutdown` / `core_provider_status` / `core_set_provider_key` / `core_clear_provider_key` | 面板 → 壳 | **8 个类型化管理命令**（替代旧 `core_action` 通用代理）：每条只映射一个 `/admin/*` 路由，参数经 serde 类型校验；载荷经 `admin_call()` 走回环 HTTP |
| `restart_core` | 面板 → 壳 | 重启核心实例；**不经** `/admin/*` |
| `core_running` | 面板 → 壳 | 查询核心是否在运行 |
| `data_dir_path` | 面板 → 壳 | 取当前数据目录路径 |
| `read_log` | 面板 → 壳 | **只读**拉取数据目录 `opencode.log` 的尾部（无参数，返回 `{ text, truncated, bytes }`，尾部截断 256KB / 1200 行） |
| `clear_log` | 面板 → 壳 | 清空数据目录 `opencode.log`（截断为空；无参数、不接受路径入参，不碰 `.previous` 存档）；文件缺失视为本就为空 |
| `open_external` | 面板 → 壳 | 用系统默认浏览器打开**四家平台的官方站点**（主机名精确白名单 `EXTERNAL_HOSTS`，禁 userinfo 与端口）；Tauri WebView 里 `target=_blank` 默认静默失败，申请 Key 的官方页必须经壳转发 |
| `ai_chat(payload)` | 面板 → 壳 | **AI 助手唯一的网络出口**：整份请求必须挂在 `payload` 键下（Tauri v2 按参数名绑定，平铺传会直接报「missing required key payload」）。壳侧用 ureq 发请求、逐行解 SSE；`tools` 非空才声明 `tools` 与 `tool_choice` |
| `ai_abort` | 面板 → 壳 | 只置取消标志，断连由流式线程下次读取时检查完成 |
| `core-status` | 壳 → 面板 | **轻量快照**（已剥掉 `activity` 与 `modelResults`，顶层 `usage` 仍随快照下发） |
| `core-activity` | 壳 → 面板 | `activity` + `modelResults` 明细（约每 500ms 轮询，仅在内容变化时发） |
| `core-failed` | 壳 → 面板 | 核心任务失败；**故障未消除期间每 ~4s 重播同一原因**（`setup` 里的那一次早于面板注册监听，必然丢失，不重播就永远看不到失败原因与重试入口） |

面板侧唯一入口是 `src/core/bridge.js` 的 `action(name, value)` / `onState(cb)` / `onDismiss(cb)` / `readLog()` / `dataDir()`（后两个为只读调用，供新增视图使用）/ `aiChat(request, onDelta)` / `aiAbort()`。面板必须把 `core-status` 与 `core-activity` 两路合并成完整状态再下发给订阅者，否则逐模型明细与活动文案永远为空。

> ⚠ `tauri.conf.json` **没有**开 `withGlobalTauri`，因此 `window.__TAURI__` 在 WebView 里是 `undefined`：`bridge.js` 的 Tauri 绑定一律来自 `@tauri-apps/*` 的按需 `import`（含 `aiChat` / `aiAbort` 用的 `invoke` 与 `listen`）。新代码若改用 `window.__TAURI__.core.invoke(...)`，调用会在起线程之前就以 `Cannot read properties of undefined` 失败——`vite build` 与 eslint（只 lint `**/*.{js,mjs}`，且不解析模板）都抓不到这类错误，只有真实 GUI 跑得出来。

> `src/core/` 是**前端内核**（IPC 边界），不是后端；后端核心在 `src-tauri/core/`。

### AI 助手通道（1.2.0，2026-10-13 版本号改判后的落点）

面板 CSP 是 `default-src 'self'`（`connect-src` 只放行 `ipc:`），WebView 里 `fetch` 任何外部端点都会被拦，因此助手的对话**只能**经壳转发：

```
AssistantView.vue（回合循环 + 逐条确认）
  → src/core/ai.js（协议与纯逻辑：工具表 / 校验 / 快照 / system prompt / 请求裁剪 / 受控 Markdown）
  → src/core/bridge.js::aiChat({ chatId, baseUrl, apiKey, selfHosted, model, messages, tools, toolChoice })
  → invoke('ai_chat', { payload })            ← 整份请求挂在 payload 键下，平铺传必报「missing required key payload」
  → src-tauri/src/lib.rs（后台线程 ureq → 逐行解 SSE）
  → 事件 ai-chunk / ai-done / ai-error / ai-aborted（按 chatId 分发，不做帧级合并）
```

两种大脑来源，由 `prefs.js` 的 `ai.brain` 决定：

| 大脑 | `selfHosted` | 端点与凭据 | 说明 |
|---|---|---|---|
| 本机免费模型 | `true` | **壳自己解析**：`resolve_self_hosted` 读运行中核心的端口，Bearer 取数据目录 `api-key` | 面板拿不到也不需要 Key；请求仍走核心的鉴权 / Origin / 并发 / 记账链路，与 WorkBuddy 的真实请求同口径进 `usage` |
| 外部 OpenAI 兼容端点 | `false` | 面板填 `baseUrl` + `apiKey`，Key **只在会话内存** | Key 没有 `prefs.js` 白名单键，结构上落不进 `localStorage`（红线 #7），重启需重填 |

三条不可放松的边界：① `validate_ai_request` 在起线程之前收形状（`AI_MAX_MESSAGES = 40`、`AI_MAX_MESSAGE_CHARS = 30000`、`AI_MAX_TOOLS = 40`，端点必须 https 或**精确回环**主机名）；② `build_ai_body` **只在 `tools` 非空时**才声明 `tools` 与 `tool_choice`，免得惊扰不支持工具的老端点；③ 助手的写类工具是**提案**——`AssistantView` 逐条勾选确认后才落到 `bridge.action`，与面板按钮走同一条类型化命令链路，模型自己**不能**执行任何本地动作。

### 动作表（面板 / 托盘动作 → 核心路由）

`docs/contract.md` 是「面板动作 → 核心路由」唯一的人工可读契约，要求 `src-tauri/src/lib.rs` 的 `ADMIN_ROUTES`、`src-tauri/core/src/server.rs` 的 `ACTION_ROUTES` 与本表三者一致。

| 动作 | HTTP 路由 | 方法 | 载荷 | 说明 |
|---|---|---|---|---|
| `refresh` | `/admin/refresh` | POST | 无 | 重新读取免费模型目录（含重启运行时） |
| `probe` | `/admin/probe` | POST | `{ "model"?: string, "providers"?: string[] }` | 探测模型：`model` 只重检一个模型，`providers` 只重取并重检指定平台（与 `model` 互斥），都不传表示探测全部；形态不对返回 202 + 错误信封，不降级成全量 |
| `import` | `/admin/import` | POST | `{ "modelsFile"?: string }` | 导入 / 切换 WorkBuddy 配置路径 |
| `system-proxy` | `/admin/system-proxy` | POST | `{ "enabled": boolean }` | 切换系统代理并重读模型 |
| `shutdown` | `/admin/shutdown` | POST | 无 | 先响应、再触发一次优雅退出 |
| `provider-status` | `/admin/provider-status` | POST | **不读请求体** | 列出四平台的 `{ id, label, configured }`；**绝不回 Key、也不回掩码尾字符** |
| `set-provider-key` | `/admin/set-provider-key` | POST | `{ "provider": string, "apiKey": string }` | 校验后原子写数据目录 `providers.json`（`0600`），返回刷新后的 `provider-status` 形态 |
| `clear-provider-key` | `/admin/clear-provider-key` | POST | `{ "provider": string }` | 只删该平台的条目（幂等），同样返回新状态 |

> ⚠ **这三条动作的链路（核心 ↔ 壳 ↔ 面板）已全部接上**：`ACTION_ROUTES` ↔ `ADMIN_ROUTES` ↔ `core_action` 由壳单测钉住，面板入口是 1.1.0 Stage 5 的 `src/views/ProvidersView.vue`；Key 的消费者是 1.1.0 Stage 3 的 `runtime.rs::providers_section_for`（经 `OPENCODE_CONFIG_CONTENT` 注入声明段）与 `Backend::models()` 的聚合发现。保存 / 清除后**自动热生效**：面板改发 `probe { providers: [<平台 id>] }`，核心侧 `orchestration.rs::probe_platforms` 先 `refresh(true, …, scope)`——**重启隔离的模型子进程**以载入新 Key（不动应用窗口），再**定向重取 + 重检那一家**，其余平台的目录与探测结果一概不动；这一家一个模型都没有时（Key 无效 / 上游没这家）探测无对象，仍会按现有发布集 `sync_published` 重发一次配置，否则插件里留的是换 Key 之前的旧条目。回应之前会查「正在停止 / 正在批量探测 / 正在读取」并当场拒成 `{error}`，否则用户会看到「已应用」却什么也没变。不再叠一轮全量 `refresh`。它们的错误码是 `invalid_provider`（id 不在注册表）与 `invalid_provider_key`（空 / 超 4096 字符 / 含控制字符），落盘失败映射为 502。凭据口径见 `AGENTS.md` 安全红线 #7。

⚠ **自动化现状（如实标注）**：原先实读三处并断言集合相等的契约测试 `src/core/test/contract.test.js` 已随 Node 核心一起归档。**代码内两张表已有自动门禁**：壳的 `src-tauri/src/lib.rs::shell_action_routes_match_the_core_contract`（`cargo test --lib`）断言 `ADMIN_ROUTES` 与核心 `ACTION_ROUTES` 逐项一致；**`docs/contract.md` 的表格是第三份手写副本，仍无校验**，改动动作表时必须人工核对。其余自动保护是 `server.rs` 内单测（每个动作路由挂在 `/admin/` 下、不与 `/v1/*` 冲突）与 `tests/red_lines.rs`。

### 鉴权与结果判据

- 所有 `/admin/*` 必须带 `Authorization: Bearer <api-key>`；**`/health` 同样需要鉴权**。key 由核心生成并写入数据目录下的 `api-key` 文件（权限 `0600`），仅本机可读。
- 核心侧比较使用 `server.rs::constant_time_eq`（`subtle::ConstantTimeEq`，定时安全）；请求带任意**非空** `Origin` 头一律 **403**。
- 壳侧调用为 `admin_call(port, key, route, body)`（回环 HTTP，默认超时 60s；`/admin/shutdown` 收紧为 5s）。成功判据以 **HTTP 状态码 2xx** 为准；非 2xx 时错误信息取响应体 `error.message`，缺省为「请求失败」。
- `/admin/shutdown` 返回非 2xx 表示核心未能优雅退出。壳侧不再有「SIGTERM → 强杀」：改为等待核心的退出回调（`set_exit_hook`，预算 10s），超时后强制关闭核心的专用 tokio 运行时（`shutdown_timeout`，在途任务被丢弃）。

## 数据目录与运行形态

两种运行形态**共用同一份编排代码，但数据目录互不相通**：

| 形态 | 入口 | 端口 | 数据目录（`api-key` / `status.json` 所在处） |
|---|---|---|---|
| 桌面壳（正式形态） | `src-tauri/src/lib.rs::start_core` → `orchestration::run(StartOptions { data_dir, port, handle_signals: false })` | `pick_port()`：默认 41980，被占用时回退到系统分配的空闲端口 | Tauri `app_data_dir`（macOS `~/Library/Application Support/app.wbbridge.desktop`，identifier `app.wbbridge.desktop`） |
| 独立核心二进制 | `src-tauri/core/src/main.rs`（`handle_signals: true`，读 `BUDDY_*` 环境变量） | `BUDDY_PORT`，默认 41980 | `BUDDY_DATA_DIR`，否则平台默认（macOS `~/Library/Application Support/Buddy Bridge`、Windows `%APPDATA%\Buddy Bridge`、Linux `${XDG_CONFIG_HOME:-~/.config}/Buddy Bridge`） |

目录内文件清单（`api-key` / `providers.json` / `service.pid` / `settings.json` / `status.json` / `opencode.log` / `runtime/<version>/opencode` / `opencode/{config,data,cache,state,project}`，目录名常量 `DATA_DIR_NAME = "Buddy Bridge"`）的用途说明、`status.json` 的 `schemaVersion` 口径、顶层 `usage` 字段与内置 `version` 历史沿革值 `0.2.0`，唯一正文在 `AGENTS.md` 的「环境变量（核心）」（目录内文件表）与「核心架构与数据流 › 关键常量」；本页不再复制。

> 排查 `/health` 时必须按运行形态取对应目录里的 `api-key`；壳形态的端口也可能不是 41980（以 `status.json` 的 `endpoint` 为准）。
