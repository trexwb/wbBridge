# 版本与发布

本页说明 WB Bridge 的版本号落点、校验与推进方式、发布流程与发布前验收清单。事实来源：根 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`、`src-tauri/core/Cargo.toml`、`src-tauri/core/src/orchestration.rs`、`scripts/*.mjs`、`.github/workflows/release.yml`、`AGENTS.md`。

## 版本号（唯一权威源：`AGENTS.md`）

`AGENTS.md` 的「当前基准版本」一节是本项目版本号规则的**唯一正文**：当前基准版本取值、7 处落点（根 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`、`src-tauri/core/Cargo.toml`，以及 `AGENTS.md` 的三行基准表）、`npm run version:check` 与 `npm run version:set -- <x.y.z>` 的用法、**强制递增规则**与豁免情形、`1.2.x ~ 1.3.x` 段位于 2026-10-13 由维护者改判后重新启用（当前基准版本即 **1.2.5**，`1.4.x` / `1.5.x` 一并弃用），全部以该节为准（`AGENTS.md` 的三行基准表同时是 `scripts/check-version.mjs` 的校验对象）。

本页只保留两条与「发布验收」直接相关的口径：

- 验收方式：`npm run version:check` 退出 0，且 `version:set` 之后 7 处取值一致。
- 面板代码没有版本字面量：版本号由 `vite.config.js` 在构建期从 `package.json` 注入 `__APP_VERSION__`；`status.json` 内写入的 `version` 是历史沿革值 `0.2.0`，与同处写入的 `schemaVersion: 1` 一起描述快照，**不属落点**。

## 发布流程

### CI 工作流

`.github/workflows/release.yml`：推送 `v*` tag 或手动 `dispatch` 触发。

三个作业的构成与闸门（test 作业的 `cargo test` + `check-version.mjs` + 八组 `node --test` 与「触发标签 ↔ `src-tauri/tauri.conf.json` 版本」闸门、平台构建作业的 `npm ci` + `npm run tauri:build -- --target <triple>` 与 macOS 的两步收尾、`update-manifest` 作为 `latest.json` 唯一写者并对账 url 末段与实际资产名），**唯一正文在 `AGENTS.md` 的「常用命令 › 签名与发布」**；本页只保留发布验收视角的产物口径：

4. 产物：六平台安装包 + 各自 `.sig` + `latest.json`，发布为 **Draft Release**（`releaseDraft: true`）；人工确认后再点 Publish。

> **发布说明**：工作流的 Release 正文是硬编码一句「WB Bridge — 让 WorkBuddy 使用 OpenCode 免费模型。」叠加 `generate_release_notes: true`（GitHub 按 commit 历史自动生成），`latest.json` **没有 `notes` 字段**——更新提示文案与发布说明无关。发布正文底本由维护者在仓库内维护（最近一份为 [`docs/release/v1.2.5.md`](../release/v1.2.5.md)；`v1.2.4.md` 未打标签，其内容已并入 1.2.5），发布时粘贴到 Release 页并人工核对。

### 签名与自动更新

自动更新的接线现状（`tauri-plugin-updater` / `tauri-plugin-process` / `createUpdaterArtifacts` / `bundle.targets` 显式列表不含 `dmg` / `plugins.updater` / capabilities 的两条声明）、签名注入包装器 `scripts/with-updater-key.mjs` 的取值优先级与「只注入、不判形态、不试签」口径、`TAURI_SIGNING_PRIVATE_KEY{,_PATH}` 的变量分工、`plugins.updater.pubkey` 只有第一条生效的换钥约束、签名期报错文案 → 成因对照（含两类会静默签成功的损坏）、私钥纪律，以及密钥生成与单独签名命令，**唯一正文在 `AGENTS.md` 的「常用命令 › 签名与发布」**；本页不再复制。

- **构建期的两类预期告警**：① `Warn skipping app notarization, no APPLE_ID & …`（ad-hoc 签名、无公证凭据，无需修，代价是 `spctl` 判定 rejected）；② macOS 27 上 `hdiutil … deprecated … use diskutil image`（产物正常，`scripts/make-dmg.sh` 暂继续用 hdiutil）。
- **Draft 语义**：`releases/latest` **不含 draft 与 prerelease** → 人工点 Publish 之前客户端检查更新必然 404，这是期望行为（draft 即灰度闸门）。
- **v1.0.1 及更早版本收不到更新**：那一版没接 updater（产物无 `.sig`、无 `latest.json`），用户只能手动下载安装包升级一次；从 v1.0.2 起才有应用内更新。

### 安装包命名

文件名模式 `{productName}_{version}_{arch}.{ext}`，版本号由源码决定；macOS 的 updater 包**唯一不带版本号**（由 CI 补架构后缀）。GitHub 侧显示的资产名会把空格规范化成 `.`，磁盘上仍是带空格的 `WB Bridge_…`。

| 系统 | 安装包 | updater 产物 |
|---|---|---|
| macOS（Apple Silicon / Intel） | `WB.Bridge_<版本>_aarch64.dmg` / `…_x86_64.dmg`（由 `make:dmg` 用 hdiutil 产出） | `WB.Bridge_aarch64.app.tar.gz` + `.sig`、`WB.Bridge_x86_64.app.tar.gz` + `.sig` |
| Windows 10/11 x64 / ARM64 | `WB.Bridge_<版本>_x64-setup.exe` / `…_arm64-setup.exe` | 同名 `.sig`；另有 `WB.Bridge_<版本>_{x64,arm64}_en-US.msi` + `.sig`（**MSI 不参与更新**） |
| Linux x64 / ARM64 | `WB.Bridge_<版本>_amd64.AppImage` / `…_aarch64.AppImage` + 各自 `.deb` | **更新包就是裸 `.AppImage` + 同名 `.sig`**（bundler 不额外产出 `.AppImage.tar.gz`）；`.deb` 的 `.sig` 不参与更新 |

> 每轮 Release 共 **23 个资产**（六平台安装包 + 各自 `.sig` + mac 两个 `.app.tar.gz(+.sig)` + `latest.json`）。macOS 的 `.dmg` **不经 Tauri**：`bundle.targets` 是显式列表且不含 `dmg`，dmg 由 `npm run make:dmg`（`scripts/make-dmg.sh`，`hdiutil create -volname <productName> -srcfolder <暂存的 app + Applications 快捷方式> -ov -format UDZO`）生成，产物 `bundle/dmg/<productName>_<version>_<arch>.dmg`；架构取 `TARGET_TRIPLE` 前缀（**CI 交叉目标必须传**，否则 `uname -m` 反映的是 runner 架构），非 macOS 平台跳过返回 0。`.rpm` 已不在 `bundle.targets` 内。

### macOS 首次打开

应用使用 ad-hoc 签名（未做 Apple 公证）。首次打开若被拦截：先尝试打开，再到「系统设置 → 隐私与安全性」点击「仍要打开」；若提示「已损坏」，确认来源可信后执行：

```sh
xattr -dr com.apple.quarantine "/Applications/WB Bridge.app"
```

### 商业签名与公证（预留位，尚未接入）

当前所有平台都**没有**商用代码签名，ad-hoc 只解决 Apple Silicon 产物"下载后被判定为损坏"，**不等于**通过 Gatekeeper。证书就绪后的接入位置：

| 平台 | 挂载位置 | 就绪后要做什么 |
|---|---|---|
| macOS 签名 | `tauri.conf.json` → `bundle.macOS.signingIdentity`（当前 `"-"`，即 ad-hoc） | 换成 Developer ID 标识；CI 侧按官方流程用 `APPLE_CERTIFICATE` / `APPLE_CERTIFICATE_PASSWORD` / `KEYCHAIN_PASSWORD` 建临时钥匙串，再把 `APPLE_SIGNING_IDENTITY` 等变量给 `npm run tauri:build` |
| macOS 公证 | **纯环境变量**，不改配置文件 | 二选一：Apple ID 路线 `APPLE_ID` + `APPLE_PASSWORD`（app-specific password）+ `APPLE_TEAM_ID`；或 App Store Connect 路线 `APPLE_API_ISSUER` + `APPLE_API_KEY` + `APPLE_API_KEY_PATH` |
| Windows 签名 | `tauri.conf.json` → `bundle.windows.certificateThumbprint` + `digestAlgorithm` + `timestampUrl` | 证书装进 runner 的证书存储、按指纹填 `certificateThumbprint`；签名后 SmartScreen 不再提示"仍要运行" |
| Linux | 无系统级签名要求 | 仅 updater 的 minisign 签名（已接线） |

> 🔴 当前被 Apple Developer Program **会员到期**卡住：无法访问 Certificates, Identifiers & Profiles ⇒ 无法创建 / 下载 Developer ID Application 证书，本机 `security find-identity -v -p codesigning` 返回 **0 个有效签名身份**。续费后照着执行的完整步骤（生成 CSR → 平台签发证书 → 导入登录钥匙串配对 → 导出 `.p12` → CI 签名 / 公证变量 → 改 `signingIdentity` 并补 `hardenedRuntime` / `entitlements` → notarytool 公证 → `.dmg` 单独公证装订 → 验证清单与回滚）见 [macOS 商业签名与公证接入指南](macOS 商业签名与公证接入指南)。键名与环境变量名取自 Tauri 官方文档（`distribute/Sign/macos` 与 `distribute/Sign/windows`），**接入前按当时文档复核**。
>
> ⚠ `tauri.conf.json` 是严格 JSON，**不能写注释**，所以预留位说明只写在本页。

### 失败路径与回滚

| 失败点 | 面板行为 | 服务影响 |
|---|---|---|
| 检查更新失败（endpoint 404 / 网络不可达 / 清单签名不符） | 「关于与更新」的更新区显示具体原因（`FeedbackBar` 错误态，可关闭）；**冷启动的静默检查失败完全不提示** | 无。探测与请求链路不经更新器 |
| 下载或安装失败（含清单 url 指向的资产名取不到） | 更新条保留、按钮回到「下载并安装」，错误可见并可原地重试（`bridge.js` 只在成功时清空 Update 句柄）；也可手动到 Release 页下载安装包 | 无。**不存在"半更新"**：安装失败即视为未安装，当前版本继续运行 |
| 装完点「重启应用」 | `process.relaunch` → `ExitRequested` → 壳的**有界**停止（`stop_core_bounded`）→ 重启 | 重启路径与关窗退出共用同一条优雅关停链，不为更新另开退出通道 |
| 更新后首启失败 | 面板收到 `core-failed`，`phase: error` + 原因（该事件在故障期每 ~4s 重播，晚挂载的监听也能收到） | 核心不重试拉起；用户可按下表回滚 |

**回滚兜底（手动装回上一版）**：每个已发布版本的安装包保留在 Release 页（Publish 后不删资产）。步骤：

1. 「关于与更新」记下当前面板版本；
2. 托盘或关窗彻底退出应用（关窗即退出，无需二次操作）；
3. 到 Release 页下载上一版安装包（macOS `.dmg` / Windows `-setup.exe`）；
4. 覆盖安装后启动。**数据目录不用动**：`api-key`、`settings.json`、`status.json` 与托管的 OpenCode 运行时都在应用数据目录，跨版本复用；
5. 若模型发布结果与新壳不一致，回到「模型与服务」点一次「读取免费模型」→「检测全部」→「导入 WorkBuddy」（核心只增删自己名下的条目）。

## 标签纪律

标签纪律的唯一正文在 `AGENTS.md` 的「Git 提交规范」一节（顺序铁律：先推进版本并提交、再在该提交上打标签；CI 的「标签 ↔ `tauri.conf.json` 版本」闸门；三个 build 作业的产物名自检与 `update-manifest` 的待核对项；已推送标签的删除 / 移动只能由维护者执行）；本页不再复制。

## 发布前检查清单（验收）

- [ ] `npm run version:check` 通过（**7 处落点**一致）
- [ ] `cargo test`（`src-tauri/core/`）三层全绿；`cargo test --lib`（`src-tauri/`）全绿
- [ ] `cargo clippy --all-targets`（核心）与 `cargo clippy --no-deps --all-targets`（壳）均 0 warning
- [ ] `npm run test:prefs`、`npm run test:ops`、`npm run test:ai`、`npm run test:prompt`、`npm run test:chat`、`npm run test:bridge`、`npm run test:manifest`、`npm run test:updater-key` 八组 JS 套件全绿；`npx eslint .` 退出 0、`npm run vite:build` 成功
- [ ] 对上一版版本号做一次文档残留扫描（如 `grep -rn "1\.1\.14" docs/ AGENTS.md README.md`），确认当前版本口径已同步
- [ ] 确认仓库级 **Variables** 已配 `TAURI_SIGNING_PRIVATE_KEY`（私钥**全文**）与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`（当前非空）。缺任一项会在整套 Rust 编译跑完后的打包那一步失败（空值报 `Missing comment in secret key`、口令错报 `Wrong password`）
- [ ] 本地按 `npm run tauri:build` / `npm run build` 走一次：核对包装器打印的「已注入内联签名私钥（来自 <文件名>）→ 公钥配对 OK」与产物 `.sig` 的签名者 key ID 是否等于 `plugins.updater.pubkey` 那条（注入器不替你挡坏私钥）
- [ ] 确认未纳入 `api-key`、`.env.local`、`status.json`、`settings.json`、私钥等敏感文件
- [ ] 按「标签纪律」的顺序：版本推进提交 → 在该提交上打标签 → 推标签
- [ ] **实机启动 GUI**：打开安装后的应用，确认面板、托盘、模型检测与导入可用
- [ ] 产出安装包并实机打开验证（macOS 已实机安装运行；**Windows / Linux 包仍待在真实机器上安装与冷启动**）
- [ ] **真实升级闭环**：在真实客户端上完成一次「检查 → 下载 → 安装 → 重启带新版本起来」（**尚未走通**，见[已知限制与未验证项](已知限制与未验证项)）
